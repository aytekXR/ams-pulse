## 3. NEW issues found in this tree

### N1 (P0) — A transient cluster-side 500 silently flips Pulse to "standalone" and poisons the mode cache

- **Where:** `server/pkg/amsclient/client.go:644-654`; consumed at `server/internal/collector/restpoller/restpoller.go:246-286`.
- **Why it's a problem:** the 404/500→standalone mapping is applied **unconditionally** — even when the `cluster-mode-status` probe just returned `success=true` (authoritative "this IS a cluster"), and even when the 500 arrives on page 2+ of pagination (discarding the 50 nodes already fetched, `return nil, nil` at `:654`). Real clusters emit exactly this: a Mongo/Redis blip or Tomcat cluster-bean restart 500s the nodes route transiently. The code then (a) returns `(nil, nil)` = success-empty, (b) **overwrites** `clusterModeIsCluster=false` at `:650-653`, short-circuiting to standalone for up to ~60 subsequent calls (~4 minutes at the observed 14 calls/min across restpoller+discovery) without re-probing. Downstream, `restpoller.go:259-286` takes the standalone branch: synthetic single-node stats, `consecAPIErrors` reset to 0 — so the D-087 failure-streak alerting **never fires**, `/healthz` stays green, and a 60-node fleet disappears from the UI with zero log lines (the client has no logger). The companion regression test passes for the wrong reason: `api_streak_test.go:483-486` still asserts "500 → real failure", but only stays green because its fixture lacks `/rest/v2/system-status` — on a real cluster the same 500 now yields a *success* event.
- **What it violates:** correctness of the F7 feature the changelog now certifies ("works against real AMS 3.x clusters"); your own architecture principle of never fabricating health (`normalize.go` "do not emit zeros"); the alerting acceptance criteria (failure-streak ladder).
- **Fix (exact):** only map 404/500→standalone when the mode is *not* authoritatively known to be cluster: `if !(known && isCluster)` guard around `:646-654`; never downgrade the cache from a data-path error — let the periodic `cluster-mode-status` probe own mode transitions. Mid-pagination errors should return `(nil, err)`. Add a `logger` to the client (or return a typed error the poller logs at Warn — it already does for `clusterErr != nil`). Fix the fixture in `api_streak_test.go` to serve `system-status` so the test actually guards this path, and add a case: probe says cluster + nodes route 500s ⇒ failure-streak event, cache still cluster.

### N2 (P0) — Every cluster node event is stamped with the same configured node ID: fleets collapse into one flickering phantom node

- **Where:** `server/internal/collector/restpoller/restpoller.go:250-252`: `ev := collector.NormalizeClusterNode(n); ev.NodeID = p.cfg.NodeID // override with our configured ID`.
- **Why it's a problem:** `NormalizeClusterNode` correctly sets `NodeID = n.PrimaryID()` (`normalize.go:258`) and the next line overwrites it with `PULSE_AMS_NODE_ID` (default `"standalone"`). Pre-D-173 this was dead code (the flat route 404'd on real 3.x); the cluster fix made it live. Against a real cluster, N nodes → N `node_stats` events per 5-second tick **all with `node_id="standalone"`**: the aggregator's full-replace keyed on NodeID makes the node card flicker to whichever node arrived last; ClickHouse receives all per-node rows collapsed onto one ID (720 rows/min at 60 nodes), poisoning per-node rollups; and because `cluster.Discovery` separately emits the same nodes under their **real** IDs every 30 s, the Fleet page shows **N+1 nodes** with one imposter. Two data paths now disagree about fleet identity.
- **What it violates:** F7 correctness; the metrics-integrity principle behind your rollup design; the changelog claim being certified into v0.4.2.
- **Fix (exact):** delete the override for the cluster branch (keep `p.cfg.NodeID` only for the standalone `NormalizeSystemStats` path, where AMS provides no ID). While in there, fix the adjacent regressions from the same wave (batched in N-cluster below): don't fabricate `disk_pct`/`net_*`/`jvm_heap`/`version` fields real AMS 3.x doesn't send (`normalize.go:261-269` — the UI renders "Disk 0%" as a measurement, and the cluster branch never calls `GetVersion`, wiping node versions the standalone path used to show).

### N3 (P1, boots-nothing) — The hardened overlay no longer starts: base-file `CLICKHOUSE_SKIP_USER_SETUP` merges into it and disables the auth it enforces

- **Where:** `deploy/docker-compose.yml:148-154` (new, correct for the base) vs `deploy/docker-compose.hardened.yml:99-109`.
- **Why it's a problem:** the documented hardened invocation layers base + hardened (`hardened.yml:3-8`). Compose merges `environment` maps per-key — keys absent from the later file survive from the earlier one, and hardened's ClickHouse block adds `CLICKHOUSE_USER`/`PASSWORD` but does **not** unset the base's new `CLICKHOUSE_SKIP_USER_SETUP: "1"` (only a comment says it "must NOT be set"). The official ClickHouse entrypoint short-circuits all user provisioning when the skip flag is set, so the named user is never created; the hardened healthcheck (`clickhouse-client --user $$CLICKHOUSE_USER …`, `:109`) then fails forever; `pulse-migrate`/`pulse` wait on `service_healthy` and never start. Net effect of the Issue-C fix: the evaluator path was repaired by breaking the hardened path — and no CI job composes base+hardened, so nothing catches it.
- **What it violates:** install-path completeness (the same criterion as Issue C); the hardened overlay's own stated contract ("auth must be enforced").
- **Fix (exact):** in `hardened.yml`'s clickhouse `environment`, explicitly neutralize the flag — `CLICKHOUSE_SKIP_USER_SETUP: ""` (empty disables it in the entrypoint), or use `environment: !override` with the full map. Add a CI `compose config` assertion (cheap) that the merged base+hardened config contains USER/PASSWORD and an empty/absent skip flag, or extend `compose-boot` with the hardened combo against mock-ams.

### N4 (P1) — The new `stream_ingest_error` events are write-only: the payload is discarded at the ClickHouse sink

- **Where:** `server/internal/store/clickhouse/clickhouse.go:467-468` (`dataJSON, _ := json.Marshal(ev.Data); _ = dataJSON`) + `contracts/db/clickhouse/0001_init.sql` (`server_events` has no data/action/stream_name columns).
- **Why it's a problem:** Issue J's fix maps the three official AMS error webhooks into a new event type, but the sink extracts only known typed columns — so `action`, `stream_name`, and `metadata` are all dropped. Stored rows are indistinguishable (`endpointFailed` vs `publishTimeoutError` vs `encoderNotOpenedError`), nothing queries `event_type='stream_ingest_error'` (no aggregator case, alert rule, API, or UI surface), and the contract wasn't finished: the schema enum gained the value but no `then` clause constrains its `data`, and no fixture exercises it (`contracts/events/fixtures/` unchanged — your own "contracts before code" rule, CLAUDE.md §2). The feature as shipped is a log line, not a capability — and the changelog sells it as "captured instead of silently dropped".
- **Fix (exact):** smallest honest fix — persist `action` into the existing `error_code`-style column if one fits, else add a migration (`0011_server_events_action.sql`: `action LowCardinality(String) DEFAULT ''`, plus `stream_name String DEFAULT ''`), populate in the sink, and add the schema `then` clause + one valid/invalid fixture pair. Then either surface it (count in ingest-health, optional alert condition) or soften the changelog line to "recorded". Also: the webhook's unknown-action log moved Debug→Info (`webhook.go:360`) — on a busy AMS emitting unmapped actions that's steady default-level noise; rate-limit or demote.

### N5 (P1) — `install.sh` now `source`s the `.env` it wrote unquoted: passwords with spaces break re-runs; `$(…)` in a password executes as shell

- **Where:** `deploy/quickstart/install.sh:206-213` (`set -a; source "$ENV_FILE"`) vs the writer at `:227-239` (`printf 'PULSE_AMS_LOGIN_PASSWORD=%s\n' "$PASSWORD"` — bare, unquoted values).
- **Why it's a problem:** the secret-key-reuse fix reads the file back with bash `source`, but the file format is Compose-env, not bash. An AMS admin password containing a space makes `source` execute the second word (→ `set -e` aborts every re-run with "command not found"); one containing `$(…)`, backticks, or `;` is **executed by the installer that wrote it** — self-inflicted command injection on re-run. First runs are unaffected, which is exactly why the quickstart's happy-path CI (still absent) wouldn't catch it. Adjacent re-run bug: `:235` unconditionally rewrites `PULSE_LICENSE_KEY=` from the (empty) flag var, wiping a key the operator added per the script's own instruction at `:338`.
- **Fix (exact):** don't `source`; extract the single needed value safely — `PULSE_SECRET_KEY="$(grep -E '^PULSE_SECRET_KEY=' "$ENV_FILE" | head -1 | cut -d= -f2-)"` (same pattern for the license key: preserve when flag empty). Alternatively write single-quoted values and keep `source`, but grep-extract is strictly safer. Add the quickstart boot job to CI including a re-run pass with a spaced password.

### N6 (P1) — Trivy moved to post-push: a HIGH/CRITICAL finding now fails the release *after* the vulnerable image is publicly pullable

- **Where:** `.github/workflows/release.yml`: pre-push local scan is now `if: github.event_name == 'workflow_dispatch'` only (`:241,256`); the tag-push path scans `…@${digest}` (`:293-315`) — which by definition runs **after** "Build and push multi-arch image" (`:270-272`) has pushed every tag including `latest`.

A failed scan leaves the vulnerable image live on GHCR under `0.4.2`/`latest` (only cosign signing and release assets are blocked), and your listing sells "Trivy-gated releases".
- **Fix (exact):** two-stage publish: push the candidate under a quarantine tag (`:candidate-<sha>` — digest is identical), Trivy the digest for both arches, then promote by pushing the real tags (`docker buildx imagetools create -t …:X.Y.Z -t …:latest …@digest`) and cosign. Or keep the current flow but add `latest`-tag promotion and GitHub-release creation *after* the scan, and document that the version tag may briefly exist unscanned.
